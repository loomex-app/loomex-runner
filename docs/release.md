# Loomex runner release and installation

Version 0.1.0 contains a private native `loomex-runner` daemon and a thin public `loomex` CLI for macOS arm64. The CLI cannot start daemon, worker, or supervisor modes. It installs without root privileges under `~/Library/Application Support/Loomex/runner`, keeps explicit state under `~/.local/share/loomex/runner`, listens on its per-user control socket, and runs `loomex-runner` as LaunchAgent `app.loomex.runner`. The package has explicit project, version, platform, and state-schema metadata; it does not migrate any earlier Loomex state.

`scripts/build-release.sh --production` requires a clean committed source revision and builds from a temporary `git archive` snapshot of that exact revision. It runs locked Cargo tests and an arm64 release build with source and home paths remapped, validates package inventory and the portable LaunchAgent template, signs both binaries with hardened runtime and a secure timestamp, creates a create-only deterministic SHA-256 inventory, signs the canonical release manifest, requires an `Accepted` Apple notarization result, and performs code-signature and Gatekeeper assessment. A byte scan rejects release payloads containing the build machine's home path. Production requires `LOOMEX_CODESIGN_IDENTITY`, `LOOMEX_NOTARY_PROFILE`, and `LOOMEX_MANIFEST_SIGNING_KEY`.

This Mac currently reports zero valid code-signing identities. Production signing, notarization, release verification, and production installation are blocked until a Developer ID Application identity, Apple notarization profile, and offline manifest-signing key are provisioned. The repository does not claim the current output is production-ready.

For isolated fixture tests only, `scripts/build-release.sh --unsigned-development` produces a native debug-profile artifact marked `developmentOnly`. This preserves the compile-time development class that permits the loopback-only `LOOMEX_DEV_API_ORIGIN`; production binaries use the release profile, a pinned HTTPS origin, and reject that override. Development installation requires both `--allow-unsigned-development` and `LOOMEX_ALLOW_UNSAFE_DEV_INSTALL=1`. Never use that mode for a normal installation or distribution.

The installer verifies signature policy, project/platform provenance, payload digest, every file digest/mode/size, safe archive members, native code signatures and Gatekeeper acceptance for production, project metadata, and the signed LaunchAgent template before moving a staged version into place. A first install refuses any preexisting runner-owned state namespace, while retries after rejected artifact verification remain clean. It derives the installation-local absolute daemon/state paths in the generated plist after verification; the plist keeps the lexical stable `current` path across upgrades. Every version moved into place is recorded immediately in a durable owned-version inventory. Activation switches the stable `current` symlink and LaunchAgent plist, then requires the new CLI to report the expected healthy daemon version before retiring old bytes. It restores the previous target and plist only after proving the candidate has zero active jobs and unloading it; otherwise it retains the current service and every version byte for safe recovery. After confirmed activation all superseded inventoried versions are removed.

Updates never stop active jobs. The installer first calls `loomex drain`, which durably closes lease admission, and only then reads `activeJobs`. When jobs remain, it leaves the current daemon and jobs running indefinitely, installs the new version without activating it, and atomically records `pending-update.json`; every superseded staged version remains in the owned-version inventory. The daemon reports `updateDeferred` from that durable state. Rerun the installer after active jobs reach zero to activate the latest verified staged version. The installer clears the durable drain marker only after stopping the old daemon and switching to the verified replacement. This policy preserves singleton journal and process ownership; there is no second daemon during drain.

Uninstall first durably drains lease admission and refuses while jobs or lifecycle writers remain. It requires the exact installation receipt, complete owned-version inventory, and a working current CLI, and validates every deletion path as a direct SemVer child without symlink traversal. Once drain reports idle, it durably records an uninstall checkpoint, stops the daemon, and runs `loomex logout --offline`. A checkpoint is reusable only while its matching persistent drain marker remains; successful activation removes both checkpoint forms before reopening admission. The native helper takes the same exclusive daemon lock, performs no job or server startup, completes remote device and child-credential revocation, and deletes the exact Loomex native credential item. A busy lock or revocation failure leaves the checkpoint, service files, receipt, versions, and credential item intact; a retry can resume offline even though the daemon is already stopped. Repeated logout after the owned credential is gone succeeds idempotently. Only after revocation and credential deletion succeed does uninstall remove the receipted plist, current link, inventoried versions, and exact runner-owned state entries, including a crash-left checkpoint temporary file. Unrelated entries inside an explicitly selected state directory are preserved. It never enumerates or deletes provider CLI credentials.

CI runs `cargo test --locked` and `scripts/test-packaging.sh` on macOS arm64. Packaging tests use explicit temporary install, state, and LaunchAgent directories, generate an ephemeral RSA key, verify deterministic signed output and tamper rejection, reject development/cache paths, prove active-job update deferral, activate after drain, force activation rollback, require revoke-before-delete, and preserve an unrelated file. A final smoke builds and installs the debug artifact in those isolated directories, starts the private daemon against a non-listening loopback origin, and requires the installed thin CLI to return a valid version and active-job count. Tests invoke no real LaunchAgent, Codex configuration, Keychain write, or production service.
