# Loomex runner release and installation

Current workspace installation and delivery status: [authoritative reliability status](../../planning/plugin-runner-integration/reliability-persona-performance-2026-10-03/current-status.md). This document describes supported mechanics; it does not establish that a candidate is installed.

Each runner release contains a private native `loomex-runner` daemon and a thin public `loomex` CLI for macOS arm64. The CLI cannot start daemon, worker, or supervisor modes. It installs without root privileges under `~/Library/Application Support/Loomex/runner`, keeps explicit state under `~/.local/share/loomex/runner`, listens on its per-user control socket, and runs `loomex-runner` as LaunchAgent `app.loomex.runner`. The package records its project, version, platform, and state-schema metadata; it preserves existing supported installation state and initializes the versioned presentation database on first use.

The production release workflow requires a cross-component qualification before
the runner is signed or published. Its manual inputs identify the plugin and
backend repositories plus their full 40-character commit SHAs. The qualification
job checks out those immutable commits, builds the plugin with Node 24.20.x,
exports the backend route contract with Python 3.12, and runs
`run-integration-compatibility-gate.sh --required`. A private component
repository must be readable through the explicitly configured,
read-only `LOOMEX_COMPONENT_READ_TOKEN`; the workflow accepts only repositories
under the `loomex-app` organization. A missing, dirty, or mismatched
component identity fails the job; runner-only CI intentionally cannot satisfy
this gate. The compatibility result is uploaded with the run as release
evidence, and the build job depends on that result.

`scripts/build-release.sh --production` requires a clean committed source revision and builds from a temporary `git archive` snapshot of that exact revision. Before compilation it records a canonical SHA-256 source-content manifest for every tracked source path and verifies the archive against it. It runs locked Cargo tests and an arm64 release build with source and home paths remapped, validates package inventory and the portable LaunchAgent template, signs all three binaries (`loomex`, `loomex-runner`, and `loomex-lifecycle-bootstrap`) with hardened runtime and a secure timestamp, creates a create-only deterministic SHA-256 inventory, signs the canonical release manifest, requires an `Accepted` Apple notarization result, and performs code-signature and Gatekeeper assessment. A byte scan rejects release payloads containing the build machine's home path. Production requires `LOOMEX_CODESIGN_IDENTITY`, `LOOMEX_NOTARY_PROFILE`, and `LOOMEX_MANIFEST_SIGNING_KEY`.

The current workspace baseline records an existing stable local development signature; availability of that identity must be rechecked when signing. It does not establish production Developer ID or notarization eligibility. Production signing, notarization, release verification, and installation remain deferred until an explicitly approved Developer ID Application identity, Apple notarization profile, and offline manifest-signing key are available and qualified. The repository does not claim development output is production-ready.

For explicitly authorized local development testing, `scripts/build-release.sh --unsigned-development` produces a native `distribution-dev` artifact marked `developmentOnly`. The script inventories every tracked path and every nonignored untracked path, including each file's content digest, size, executable mode, source class, and symlink target where applicable. It builds from a temporary snapshot of that exact inventory, embeds the canonical source-content manifest, and binds its digest into the release envelope. `artifact.py verify --source-root PATH` can then prove that a candidate matches the complete selected source content and rejects a content edit even when the filename is unchanged. The dedicated Cargo profile inherits `dev`, uses optimization level 2, debug level 1, disables incremental compilation, preserves debug assertions and overflow checks, and retains inherited panic behavior. All three binaries are packaged from `target/distribution-dev`; ordinary developer builds and production release builds keep their existing profiles. Additive `metadata/project.json` build fields record the profile, optimization level, debug assertions, and development classification. `loomex diagnostics` reports compile-time CLI build information; it does not infer the daemon build from the CLI. This preserves the compile-time development class that permits a loopback-only API origin; production binaries use the release profile, a pinned HTTPS origin, and reject that override. Development installation requires `--allow-unsigned-development`, `LOOMEX_ALLOW_UNSAFE_DEV_INSTALL=1`, and an explicit `--development-api-origin http://127.0.0.1:PORT`. The installer accepts only a root HTTP(S) URL whose host is `localhost`, a subdomain of the reserved `.localhost` namespace, or a loopback IP address; credentials, paths, queries, fragments, and non-loopback hosts are rejected. It canonicalizes the value and writes it only to this LaunchAgent's environment and its derived installation receipt so stopped-daemon offline revocation can use the same origin. It never changes the global launchd environment. This loopback testing artifact remains unsigned development output and is not a production claim or public cloud preview. The separate `--unsigned-cloud-preview` policy described in [public distribution](public-distribution.md) binds a configured cloud HTTPS origin and frozen paired distribution set.

For repeated development upgrades that must retain access to the same macOS
Keychain item, set `LOOMEX_DEVELOPMENT_CODESIGN_IDENTITY` to one persistent local
code-signing identity before building. The optional
`LOOMEX_DEVELOPMENT_CODESIGN_KEYCHAIN` selects a specific signing keychain; the
build never creates or exports an identity. All three native binaries are
signed after stripping, and the inventoried
`metadata/development-signing.json` records their exact designated
requirements. This is still a `developmentOnly` release with an unsigned
release envelope, and is not a substitute for production Developer ID signing
or notarization. A development upgrade compares the verified candidate
daemon's requirement with the installed daemon before any lifecycle intent or
drain. Identical signed requirements can proceed. A changed identity, an
unsigned downgrade, or different ad-hoc binary fails closed. Repeating the
exact same ad-hoc binary is permitted for idempotent repair.

The first upgrade from an existing ad-hoc daemon to a stably signed development
daemon is a separate, explicit trust transition. Run the installer with
`--authorize-keychain-transition` only in a foreground user session after
reviewing the candidate package and signer. The bootstrap runs the exact
candidate daemon binary in a read-only probe that may display macOS Keychain
authorization UI, then requires that same binary to pass a normal
noninteractive read before it can enter the lifecycle transaction. The probe
returns only a fixed status; it never prints, saves, deletes, copies or exports
the credential. If the user declines, the item is unavailable, the prompt
times out, or the noninteractive recheck fails, installation stops before
service changes. Subsequent upgrades use requirement equality without UI.
The consent behavior of a particular macOS Keychain ACL must be qualified with
a disposable fixture before relying on this transition for an installed item.

Public development qualification requires this existing persistent identity for all three binaries. Both the clean local deployment build and cloud preview build fail before compilation when `LOOMEX_DEVELOPMENT_CODESIGN_IDENTITY` is missing, ad-hoc or unavailable. The public packager and publication inspector independently verify actual signatures and exact inventory-bound requirements against that approved certificate. They accept an explicit `LOOMEX_DEVELOPMENT_CODESIGN_FINGERPRINT` SHA1 pin without requiring the private signing identity; a fingerprint selected through `LOOMEX_DEVELOPMENT_CODESIGN_IDENTITY` also needs no identity lookup for verification. Building still requires the available selected private-key identity and checks any supplied fingerprint against it. Identity discovery intentionally omits `security find-identity -v`: an approved self-signed identity reported as `CSSMERR_TP_NOT_TRUSTED` remains eligible without Apple trust or any trust-store mutation. Ordinary isolated `--unsigned-development` test builds without a qualified deployment profile may remain unsigned. No builder creates a certificate, changes a keychain or exports private keys. The existing approved self-signed identity requires no Apple account; production signing remains deferred.

The predecessor matrix for a new paired candidate must include these disposable-fixture cases. Every rejection must leave current targets, owner journals, drains and state unchanged, and both owner preflights must complete before paired runner activation. These requirements describe qualification evidence to collect; they do not claim a live machine or real credential migration was tested.

| Installed predecessor | Expected preflight / install result |
| --- | --- |
| No installation | Both owners eligible; normal first install and healthy readback. |
| Previously signed 1.2.5 with the same approved development signer | Native owner compares actual requirements; upgrade proceeds only on equality even if the historical envelope lacks the new signing metadata. |
| Same current signed version and exact bytes | Idempotent repair; no signer transition. |
| Signed version with another identity, or signed-to-unsigned downgrade | Reject before intent, drain, service change or plugin activation; explicit transition flag cannot bypass policy. |
| Exact same ad-hoc binary | Existing native idempotent repair policy remains; this is ineligible for a new public candidate. |
| Ad-hoc predecessor to approved persistent development signer | Without authorization reject before mutation. With explicit `--authorize-keychain-transition`, preflight reports the pending credential prerequisite; actual native install requires its foreground consent probe and noninteractive recheck before activation. |
| Pending runner/plugin operation for the exact manifest, base and retained cache path | Preserve authoritative owner journal and resume through that owner; read-only preflight does not reconcile or replace it. |
| Pending operation for a different manifest, release path or base | Reject before either selected owner mutates. |
| Runner healthy, plugin activation or Codex registration failed | Report partial completion, retain runner and exact prerequisites, retry the same set. |

Published 1.2.6 is immutable. New qualification is performed on a new candidate; no build, tag or upload replaces those published bytes.

All newly created artifacts require the canonical source-content manifest. Verification also requires that provenance by default. The explicit `--allow-legacy-source-provenance` option on `artifact.py verify` or `extract`, paired with the same option on `validate_package.py`, is reserved for inspecting historical envelopes created before source-content binding existed; it does not make a legacy artifact eligible for production publication or installation.

The installer verifies signature policy, project/platform provenance, payload digest, every file digest/mode/size, safe archive members, native code signatures and Gatekeeper acceptance for production, project metadata, and the signed LaunchAgent template before moving a staged version into place. A first install refuses any preexisting runner-owned state namespace, while retries after rejected artifact verification remain clean. Before staging bytes, it writes an exact verified-release installation journal; an interrupted first install can resume only with that same release, then retains the journal and owned-version inventory through activation before removing the journal at terminal success or a proved rollback. It derives the installation-local absolute daemon/state paths and any authenticated development-only loopback origin in the generated plist after verification; the plist keeps the lexical stable `current` path across upgrades. Optional repeated `--provider-executable PROVIDER=/absolute/path` arguments support `codex`, `claude`, `gemini`, and `antigravity` (the `agy` executable): the installer canonicalizes and validates each executable, persists the map in its owned receipt, and renders explicit provider-specific LaunchAgent environment variables. Omitting these arguments on an update preserves the installed map; providers with no explicit entry retain standard discovery. Every version moved into place is recorded immediately in a durable owned-version inventory. Activation switches the stable `current` symlink and LaunchAgent plist, then requires the new CLI to report the expected healthy daemon version before completing activation. It restores the previous target and plist only after proving the candidate has zero active jobs and unloading it; otherwise it retains the current service and every version byte for safe recovery. After confirmed activation, superseded inventoried versions remain retained until an explicitly requested, qualified lifecycle prune or uninstall.

Updates never stop active jobs. The installer first calls `loomex drain`, which durably closes lease admission, and only then reads `activeJobs`. When jobs remain, it leaves the current daemon and jobs running indefinitely, installs the new version without activating it, and atomically records `pending-update.json`, including the validated provider executable map intended for that candidate; every superseded staged version remains in the owned-version inventory. The daemon reports `updateDeferred` from that durable state. Rerun the installer after active jobs reach zero to activate the latest verified staged version. The installer clears the durable drain marker only after stopping the old daemon and switching to the verified replacement. This policy preserves singleton journal and process ownership; there is no second daemon during drain.

Uninstall is owned by the native bootstrap and its versioned recovery journal. It drains admission, records verified stop evidence, and delegates credential maintenance to the exact verified daemon executable using receipted configuration. Remote revocation is durably distinguished from local credential removal before inventory-bound quarantine cleanup. Stopped retries do not require a live socket; uncertain operations retain their original identities. Stable singleton lock inodes are not unlinked during cleanup. See [installation and removal recovery](lifecycle-recovery.md) for preflight, interrupted cleanup, explicit recovery of older prepared journals, credential diagnostics and qualification limits.

Distribution profile contract checks run with `python3.12 scripts/test_distribution_profile.py`; additionally run `cargo +1.88.0 test --locked --profile distribution-dev --bin loomex` and `cargo +1.88.0 test --locked --profile distribution-dev --lib api::tests` to exercise compiled profile diagnostics and endpoint guards. CI runs `cargo fmt --all --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo test --locked`, and `scripts/test-packaging.sh` on macOS arm64. Packaging tests use explicit temporary install, state, and LaunchAgent directories, generate an ephemeral RSA key, verify deterministic signed output and tamper rejection, prove tracked and untracked source-content mismatch rejection, reject development/cache paths and invalid provider executable configuration, prove provider binding preservation through deferred updates and activation rollback, prove active-job update deferral, activate after drain, force activation rollback, require revoke-before-delete, preserve an unrelated file, and enforce development-origin classification and loopback syntax. A final smoke builds and installs the `distribution-dev` artifact in those isolated directories, reads the canonical origin from the rendered plist, starts the private daemon against that non-listening loopback origin, and requires the installed thin CLI to return a valid version and active-job count. Tests invoke no real LaunchAgent, Codex configuration, Keychain write, or production service.

The local-control export preserves the credential-free `connection.get` projection and scoped `follow.session.lifecycle` guard. A runner-issued response handoff records a durable pending receipt before the app posts its chat message because `ui/message` is not a documented `UserPromptSubmit` callback source. Start first uses app-only, non-idempotent `runs.start_handoff.issue`; its opaque reference alone has no authority. The mounted app records the explicit Start gesture with app-only `runs.start_handoff.approve` through the MCP bridge and owner-checked local-control socket, after which chat carries the reference to `runs.start_handoff.commit`. There is no browser loopback approval endpoint or volatile approval capability. Approval is non-idempotent and must not be automatically replayed after an ambiguous response. A pending handoff has no workspace-derived hook authority: only an exact associated `loomex_run_wait` call promotes it to the native Codex session, consumes the pending record, and enables later lifecycle hooks. A UI handoff is never a Codex task identity and cannot initialize recovery scheduling. `follow.sqlite3` and `recovery.sqlite3`, with their SQLite sidecars, are part of the exact owned-state inventory exercised by packaging tests.

## Native lifecycle administration

The packaged `loomex lifecycle` surface provides `status`, `resume`, `rollback`, and `repair`, with `--json` for automation and readable status by default. It persists `app.loomex.runner.lifecycle-operation/v1` records under a separate OS-backed `lifecycle.lock`; this lock never overlaps `daemon.lock`, so lifecycle administration cannot claim workflow execution ownership. It records a staged plist digest and prior plist digest before mutating either resource, uses a fsynced temporary replacement for plist changes, and reconciles `current`, plist bytes, launchd state, and daemon health rather than trusting a stale journal phase.

An installer retry for an already completed exact package verifies the owned target, plist and live candidate before finalizing its receipt; it does not start a second service switch. If an interrupted lifecycle retry leaves that exact candidate drained with zero active jobs, `repair` clears the stale drain marker, restarts the registered service and verifies health before marking the journal complete. A different package or any active job cannot use this recovery path.

After a recorded startup-health failure, `resume` first rechecks the exact loaded candidate and captured authentication identity. A recovered Keychain authorization can allow that same operation to complete without rollback. A candidate left drained by interrupted recovery uses the existing owned, idle restart path, followed by authentication verification. An old failure checkpoint never proves a current failure; missing ownership, active work, changed authentication or unavailable health cannot establish completion.

New envelopes carry a manifest-bound, signed `loomex-lifecycle-bootstrap` sidecar and the same executable inside the payload. The thin launchers verify the sidecar digest (and the production manifest signature) before `exec`ing it. The bootstrap then verifies the envelope again, extracts and inventories the payload, renders the LaunchAgent, and invokes the private native activation transaction. The new-package path has no system Python, npm, or source-checkout dependency; the packaging suite copies the launcher away from the repository and puts a failing `python3` first on `PATH` to prove it. Envelopes created before the sidecar remain an explicitly constrained legacy migration path: their launchers retain sealed v1 journals and may use the checked-in Python helpers, but never bridge into a native operation.

The current bootstrap uninstaller writes `app.loomex.runner.bootstrap-uninstall/v2` and a private lifecycle refusal fence before side effects. The explicit recovery route reads supported historical v1 prepared records without rewriting their original evidence. Older revoked labels without bound proof remain insufficient. File inventories, deletion-start checkpoints and exact surviving-file validation permit partial cleanup to resume. Synthetic package faults do not establish real native-store or LaunchAgent qualification.

`lifecycle rollback --to VERSION` validates the owned package metadata and installed-byte digest, then uses the same native transaction as activation: drain and idle proof, LaunchAgent stop, `current` and plist transition, candidate bootstrap, and expected-version health proof. The operation record retains the prior target and plist backup before the first service action. A failed candidate is restored only after its idle state is proven; otherwise the record remains `recovery_required` and preserves every resource for `resume` or `repair`.

Production builds also require explicit LOOMEX_API_ORIGIN and LOOMEX_WEB_APP_ORIGIN HTTPS origins. CI supplies these from repository variables. The build rejects missing or malformed values before signing so an artifact cannot silently ship without its backend connection or browser destination. These non-secret destinations still require deployment qualification.

## Public paired preview candidates

See [public distribution](public-distribution.md) for the separate frozen release-set contract and unified native installer. The production gate uses sibling `runner-source` and `component-inputs` checkouts so clean runner qualification includes no nested Git repositories. The preview workflow reuses the required gate, preserves build-before-export ordering and emits build-once reviewable assets. Public staging and publication require separate exact-digest operator checkpoints; no GitHub release is created by the build workflow.

Public local development qualification uses `scripts/build-release.sh --unsigned-development --local-development-api-origin http://127.0.0.1:28080/` from clean committed source with `LOOMEX_API_ORIGIN` unset. Its `metadata/local-development-origin.json` is part of the artifact inventory and binds the optional compiled frontend origin exactly. This is an unsigned development release, including when the existing local identity signs its native executables. The release-set v2 profile delegates to the existing bootstrap `--development-api-origin` option and retains both unsafe preview opt-ins. A compatible local backend must already be running; publication and local installation use the same reviewed artifact bytes.

Cross-release retained-work recovery uses the existing Inspect and Reconcile
commands. The paired result contract is `app.loomex.paired-install-result/v4`;
maintenance ownership is reported separately from historical bootstrap ownership
through `app.loomex.runner.uninstall-work-reference/v1`. Native work v2 reports
support verified successor generations; legacy v1 reports remain readable without
cross-release handover authority. Inspect is read-only. A settled older generation
requires Reconcile with the verified candidate, followed by a fresh Inspect and
retirement review. Active or uncertain attempts retain their original release.
Maintenance completion does not install a candidate or prove cleanup eligibility;
after work resolves, use the existing uninstall recovery flow. Fixture transport
tests verify delegation and projection only; native recovery tests establish the
owner-generation transition.
