# Loomex runner release and installation

Version 0.3.9 contains a private native `loomex-runner` daemon and a thin public `loomex` CLI for macOS arm64. The CLI cannot start daemon, worker, or supervisor modes. It installs without root privileges under `~/Library/Application Support/Loomex/runner`, keeps explicit state under `~/.local/share/loomex/runner`, listens on its per-user control socket, and runs `loomex-runner` as LaunchAgent `app.loomex.runner`. The package has explicit project, version, platform, and state-schema metadata; it preserves existing supported installation state and initializes the versioned presentation database on first use.

The production release workflow requires a cross-component qualification before
the runner is signed or published. Its manual inputs identify the plugin and
backend repositories plus their full 40-character commit SHAs. The qualification
job checks out those immutable commits, builds the plugin with Node 24.20.x,
exports the backend route contract with Python 3.12, and runs
`run-integration-compatibility-gate.sh --required`. A private component
repository must be readable through the explicitly configured,
read-only `LOOMEX_COMPONENT_READ_TOKEN`; the workflow accepts only repositories
under the `loomex-app` organization. A missing, dirty, or mismatched
component identity fails the job; runner-only CI intentionally cannot satisfy
this gate. The compatibility result is uploaded with the run as release
evidence, and the build job depends on that result.

`scripts/build-release.sh --production` requires a clean committed source revision and builds from a temporary `git archive` snapshot of that exact revision. Before compilation it records a canonical SHA-256 source-content manifest for every tracked source path and verifies the archive against it. It runs locked Cargo tests and an arm64 release build with source and home paths remapped, validates package inventory and the portable LaunchAgent template, signs both binaries with hardened runtime and a secure timestamp, creates a create-only deterministic SHA-256 inventory, signs the canonical release manifest, requires an `Accepted` Apple notarization result, and performs code-signature and Gatekeeper assessment. A byte scan rejects release payloads containing the build machine's home path. Production requires `LOOMEX_CODESIGN_IDENTITY`, `LOOMEX_NOTARY_PROFILE`, and `LOOMEX_MANIFEST_SIGNING_KEY`.

This Mac currently reports zero valid code-signing identities. Production signing, notarization, release verification, and production installation are blocked until a Developer ID Application identity, Apple notarization profile, and offline manifest-signing key are provisioned. The repository does not claim the current output is production-ready.

For explicitly authorized local development testing, `scripts/build-release.sh --unsigned-development` produces a native debug-profile artifact marked `developmentOnly`. The script inventories every tracked path and every nonignored untracked path, including each file's content digest, size, executable mode, source class, and symlink target where applicable. It builds from a temporary snapshot of that exact inventory, embeds the canonical source-content manifest, and binds its digest into the release envelope. `artifact.py verify --source-root PATH` can then prove that a candidate matches the complete selected source content and rejects a content edit even when the filename is unchanged. This preserves the compile-time development class that permits a loopback-only API origin; production binaries use the release profile, a pinned HTTPS origin, and reject that override. Development installation requires `--allow-unsigned-development`, `LOOMEX_ALLOW_UNSAFE_DEV_INSTALL=1`, and an explicit `--development-api-origin http://127.0.0.1:PORT`. The installer accepts only a root HTTP(S) URL whose host is `localhost` or a loopback IP address; credentials, paths, queries, fragments, and non-loopback hosts are rejected. It canonicalizes the value and writes it only to this LaunchAgent's environment and its derived installation receipt so stopped-daemon offline revocation can use the same origin. It never changes the global launchd environment. This artifact remains unsigned development output and is not a production claim or distributable release.

All newly created artifacts require the canonical source-content manifest. Verification also requires that provenance by default. The explicit `--allow-legacy-source-provenance` option on `artifact.py verify` or `extract`, paired with the same option on `validate_package.py`, is reserved for inspecting historical envelopes created before source-content binding existed; it does not make a legacy artifact eligible for production publication or installation.

The installer verifies signature policy, project/platform provenance, payload digest, every file digest/mode/size, safe archive members, native code signatures and Gatekeeper acceptance for production, project metadata, and the signed LaunchAgent template before moving a staged version into place. A first install refuses any preexisting runner-owned state namespace, while retries after rejected artifact verification remain clean. Before staging bytes, it writes an exact verified-release installation journal; an interrupted first install can resume only with that same release, then retains the journal and owned-version inventory through activation before removing the journal at terminal success or a proved rollback. It derives the installation-local absolute daemon/state paths and any authenticated development-only loopback origin in the generated plist after verification; the plist keeps the lexical stable `current` path across upgrades. Optional repeated `--provider-executable PROVIDER=/absolute/path` arguments support `codex`, `claude`, `gemini`, and `antigravity` (the `agy` executable): the installer canonicalizes and validates each executable, persists the map in its owned receipt, and renders explicit provider-specific LaunchAgent environment variables. Omitting these arguments on an update preserves the installed map; providers with no explicit entry retain standard discovery. Every version moved into place is recorded immediately in a durable owned-version inventory. Activation switches the stable `current` symlink and LaunchAgent plist, then requires the new CLI to report the expected healthy daemon version before retiring old bytes. It restores the previous target and plist only after proving the candidate has zero active jobs and unloading it; otherwise it retains the current service and every version byte for safe recovery. After confirmed activation all superseded inventoried versions are removed.

Updates never stop active jobs. The installer first calls `loomex drain`, which durably closes lease admission, and only then reads `activeJobs`. When jobs remain, it leaves the current daemon and jobs running indefinitely, installs the new version without activating it, and atomically records `pending-update.json`, including the validated provider executable map intended for that candidate; every superseded staged version remains in the owned-version inventory. The daemon reports `updateDeferred` from that durable state. Rerun the installer after active jobs reach zero to activate the latest verified staged version. The installer clears the durable drain marker only after stopping the old daemon and switching to the verified replacement. This policy preserves singleton journal and process ownership; there is no second daemon during drain.

Uninstall first durably drains lease admission and refuses while jobs or lifecycle writers remain. It requires the exact installation receipt, complete owned-version inventory, and a working current CLI, and validates every deletion path as a direct SemVer child without symlink traversal. Once drain reports idle, it durably records an uninstall checkpoint and a sealed cleanup journal, stops the daemon, and runs `loomex logout --offline`. A checkpoint is reusable only while its matching persistent drain marker remains; successful activation removes both checkpoint forms before reopening admission. The native helper takes the same exclusive daemon lock, performs no job or server startup, completes remote device and child-credential revocation, and deletes the exact Loomex native credential item. A busy lock or revocation failure leaves the checkpoint, service files, receipt, versions, and credential item intact; a retry can resume offline even though the daemon is already stopped. Repeated logout after the owned credential is gone succeeds idempotently. Once revocation succeeds, the cleanup journal preserves the validated inventory across interruption, including after the current link has been removed; receipt and owned-version metadata remain until final state cleanup. Only then does uninstall remove the receipted plist, current link, inventoried versions, and exact runner-owned state entries, including crash-left journal and checkpoint temporary files. Unrelated entries inside an explicitly selected state directory are preserved. It never enumerates or deletes provider CLI credentials.

CI runs `cargo fmt --all --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo test --locked`, and `scripts/test-packaging.sh` on macOS arm64. Packaging tests use explicit temporary install, state, and LaunchAgent directories, generate an ephemeral RSA key, verify deterministic signed output and tamper rejection, prove tracked and untracked source-content mismatch rejection, reject development/cache paths and invalid provider executable configuration, prove provider binding preservation through deferred updates and activation rollback, prove active-job update deferral, activate after drain, force activation rollback, require revoke-before-delete, preserve an unrelated file, and enforce development-origin classification and loopback syntax. A final smoke builds and installs the debug artifact in those isolated directories, reads the canonical origin from the rendered plist, starts the private daemon against that non-listening loopback origin, and requires the installed thin CLI to return a valid version and active-job count. Tests invoke no real LaunchAgent, Codex configuration, Keychain write, or production service.

The 0.3.9 local-control export preserves the credential-free `connection.get` projection and scoped `follow.session.lifecycle` guard. A runner-issued UI handoff now activates its durable follow record before the app posts its chat message. This is necessary because `ui/message` is not a documented `UserPromptSubmit` callback source. The later Stop hook recovers a single active UI handoff only when its canonical workspace matches; ambiguity between concurrent follows fails open rather than blocking an unrelated chat. `follow.sqlite3` and `recovery.sqlite3`, with their SQLite sidecars, are part of the exact owned-state inventory exercised by packaging tests.

## Native lifecycle administration

The packaged `loomex lifecycle` surface provides `status`, `resume`, `rollback`, and `repair`, with `--json` for automation and readable status by default. It persists `app.loomex.runner.lifecycle-operation/v1` records under a separate OS-backed `lifecycle.lock`; this lock never overlaps `daemon.lock`, so lifecycle administration cannot claim workflow execution ownership. It records a staged plist digest and prior plist digest before mutating either resource, uses a fsynced temporary replacement for plist changes, and reconciles `current`, plist bytes, launchd state, and daemon health rather than trusting a stale journal phase.

New envelopes carry a manifest-bound, signed `loomex-lifecycle-bootstrap` sidecar and the same executable inside the payload. The thin launchers verify the sidecar digest (and the production manifest signature) before `exec`ing it. The bootstrap then verifies the envelope again, extracts and inventories the payload, renders the LaunchAgent, and invokes the private native activation transaction. The new-package path has no system Python, npm, or source-checkout dependency; the packaging suite copies the launcher away from the repository and puts a failing `python3` first on `PATH` to prove it. Envelopes created before the sidecar remain an explicitly constrained legacy migration path: their launchers retain sealed v1 journals and may use the checked-in Python helpers, but never bridge into a native operation.

The bootstrap uninstaller writes `app.loomex.runner.bootstrap-uninstall/v1` before draining. It records only the exact v2 receipt and owned-version inventory, repeats that validation before every destructive cleanup, persists `revoked` only after offline credential revocation, and resumes cleanup from that sealed record after interruption. It verifies that launchd actually unloaded the label before revocation and deletes no provider CLI credentials or unlisted files. Its test-mode path exists solely for isolated filesystem tests; normal uninstall always drains, verifies idle work, stops launchd, and performs offline revocation.

`lifecycle rollback --to VERSION` validates the owned package metadata and installed-byte digest, then uses the same native transaction as activation: drain and idle proof, LaunchAgent stop, `current` and plist transition, candidate bootstrap, and expected-version health proof. The operation record retains the prior target and plist backup before the first service action. A failed candidate is restored only after its idle state is proven; otherwise the record remains `recovery_required` and preserves every resource for `resume` or `repair`.
